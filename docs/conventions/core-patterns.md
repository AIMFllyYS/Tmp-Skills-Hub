# 确定性内核关键模式

> 本文档是 `AGENTS.md` 中「确定性内核铁律」的完整版。
> 这些不是风格偏好,是数据一致性约束——违反任意一条,「同一 skill 跨机器同哈希、跨 Agent 不漂移」就破功。
> 语义来源:架构初始规范 §3(资产模型)、§4(五个操作)。

## 一、store 不可变（immutable store）

- skill 收进统一库存后**不被原地修改**。更新 = 产生新内容哈希的新版本,不覆盖旧版。
- 这是「哈希 ↔ skill 对照表」成立的前提:同样的内容 → 同样的哈希 → 同样的行为(content-addressable,借鉴 Nix 思想,但不依赖 Nix)。
- 用户在任何 Agent 里"改 skill",改的是 symlink 指向的原件;原件变了,重新入库就是新版本。回滚 = 把链接指回旧版本,免费获得。

## 二、symlink 集合原子切换

变更某个 Agent 目录下的链接集合时,**禁止逐个增删**。标准流程:

1. 在临时目录构建完整的新链接集合;
2. 一次重命名替换(`active` → `active.old`,`active.new` → `active`);
3. 清理旧目录。

任何时刻观察者看到的都是一个完整集合,不存在"换了一半"的中间状态。中途失败 = 全量回滚,不落半成品。

## 三、哈希确定性

`hashSkillFolder`(packages/core/src/hash.ts)的三条不变量:

1. **顺序无关**:文件按 POSIX 风格相对路径字典序排序后哈希,与目录遍历顺序、操作系统路径分隔符无关;
2. **路径参与哈希**:每个文件哈希 `相对路径 + "\0" + 内容`,区分「同内容不同文件名」;
3. **哈希原始字节,不做换行归一化**:跨机器换行一致由仓库层保证(`.gitattributes` 统一 LF),不在哈希层做变换——哈希层的变换会让"磁盘上的内容"和"身份"脱钩,排查问题时无法对账。

忽略项(`.git`、`node_modules` 等)的清单变更等于**全库哈希迁移**,必须走 issue 评审。

## 四、Windows 符号链接

- 本地开发环境是 Windows:普通用户创建 symlink 需要开发者模式或管理员权限。
- **目录链接优先用 junction**(`fs.symlink(target, path, "junction")`),不需要提权,各 Agent 读目录内容的行为一致。
- 落地前有单独的 spike issue 验证各 Agent 对 junction 的兼容性(计划 M1 前置项)。
- store 内部不允许出现链接;扫描时遇到链接不展开,交给上层校验报错。

## 五、智能层写成 Skill,不写成代码

来自 SPM 设计的核心主张,skill-hub 沿用:**只有 Agent 做不了的事才写成代码**。

| 写成代码(core/cli) | 写成 Skill(交给 Agent) |
|---|---|
| store 增删、哈希、lockfile —— 需要原子性与精确性,不能有幻觉 | 健康检查、安全审查 —— 读文本做判断 |
| symlink 增删 —— 必须快速、原子、确定 | 分类/tag 建议、"有用"判定 —— 语义理解 |
| 本地数据服务 —— 会话之外运行 | 收录时的对话式引导 —— 天然对话能力 |

判断口径:**错了会破坏数据一致性的,进 core;错了只是建议不好的,写 Skill。**

## 六、已验证的平台事实（引用时不必重新验证）

- Claude Code 只有 `--add-dir` 指定的目录支持 skill **热加载**;默认 `.claude/skills/` 只在启动时读取。链接挂载位置的设计要考虑这一点。
- `SKILL.md` 的 `name` + `description` 是所有客户端都能读的通用层;各家 YAML 扩展(display name 等)是适配层,缺失不影响可用性,**不是收录门槛**。
